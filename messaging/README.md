# Titan messaging (Lane 5)

This service uses **Photon 2.0 Beta** (`@photon-ai/api`), with outbound API calls and inbound Socket.IO event delivery. The teammate approved replacing Stable `spectrum-ts` and ngrok with this transport. The brain HTTP contracts are unchanged. No tunnel is required.

## Run

```sh
cd messaging
npm ci
cp .env.example .env # only if you have not configured .env yet
# Fill in Photon project credentials, the existing agent handle,
# teammate allowlist and USER_PHONE_usr_maya. Keep secrets out of git/chat.
npm run dev
```

Node 22+ is required. Keep the mock brain running on port 8000 (`bash scripts/dev.sh` from the repository root starts both services once `.env` is configured). Only run one messaging process for a project and state directory.

`PHOTON_AGENT_HANDLE` is Titan's existing Photon number in E.164 format. `USER_PHONE_usr_maya` is the teammate-owned test phone, also in E.164. Add that same test phone to `OUTBOUND_ALLOWLIST`. The API key requires `project:read` and `project:write`. This service does not purchase or provision lines.

On a shared iMessage line, the teammate must have an active assignment and must message the line first. Send `ping` (case-insensitive) to receive the fixed Titan hello. `npm run hello` can recover a recent missed ping using the API; it replies only to a matching allowlisted ping from the last 15 minutes, with a stable idempotency key.

## Brain integration

The brain calls `POST http://localhost:8200/internal/send` with the existing `SendRequest`. The listener binds only to loopback. JSON Schema validation reads `../contracts/schema.json`; `src/contract-types.ts` is copied unchanged from generated contract types. The service maps the synthetic user to the configured teammate and resolves the real direct Photon conversation. It refuses other recipients and message text containing links or requests for secrets.

```sh
# From the repository root; sends a real alert to the configured teammate:
curl -X POST localhost:8200/internal/send \
  -H 'content-type: application/json' \
  -d @contracts/fixtures/send.alert.json
```

A 200 means Photon accepted asynchronous dispatch; it is not proof of phone delivery. Stable request hashes make brain retries idempotent at Photon. For a fresh run, use a real case ID generated by `/demo/play/t2`, rather than repeatedly sending an identical fixture.

Inbound `message.received` events are resolved through the authenticated Photon API and checked for project, agent line, direct conversation, human sender, and allowlisted user. Customer replies go to **only `POST /events`**, with a deterministic `event_id` derived from the provider message ID. This deviation from the brief was explicitly approved: the brain already appends the event's reply to the case, so calling `/cases/{id}/events` as well would duplicate it.

Exact YES/NO/REPORT/UNDO are recognized without a model. Configure `NVIDIA_API_KEY` for free-form interpretation by Nemotron Nano. If Nano is unavailable, the text is still recorded on the case and no approval is inferred. Disclosures such as “I told him my PIN” remain information. REPORT/UNDO are forwarded to the brain; messaging does not invent carrier actions.

Messaging never calls `/actions/{id}/approve` or `/reject`, even if SendRequest includes an action_id. It binds retries to the original case and forwards a deterministic customer.reply event only. The brain wakes an awaiting workflow and maps recovery replies to its next pending action, preventing double approvals. Legacy checkpoints containing action/intent metadata are safe to load; those fields are ignored.

## Replay and privacy

Socket.IO authenticates with the project API key over TLS; there is no inbound HTTP webhook or HMAC handler. Each reconnect subscribes after the last successfully processed cursor, pinned to event contract `2026-07-01`. Processing is serialized with at most 128 queued events. Handler/checkpoint failures stop the process rather than advancing the cursor; restart after resolving the error. Network reconnects are owned by Socket.IO.

`.state/<project>/checkpoint.json` contains cursors, hashes of processed provider IDs, and case bindings. It contains no phone numbers or message bodies. The key and raw teammate number live only in local `.env`; message text is sent only to Photon, NVIDIA for the conversation turn, and the brain/case. Never run multiple writers on the same state directory. Do not delete checkpoints during a live case; replay depends on them. A new consumer with cursor 0 has no durable replay history until an event is processed.

Logs contain fixed event/error categories, sequence numbers and provider request IDs, without message bodies or raw numbers. Provider exception bodies are never logged.

## Verification and remaining scope

```sh
npm run check
npm test
```

Tests cover schema validation, unsafe output, recipient/line/group filtering, deduplication after restart, ambiguous event responses, verbatim YES/NO forwarding without action calls, forwarded links, and disclosures without local classification. Brain recovery tests live in agent/test_workflow_offline.py.

For the brain regression check on a laptop with live agent/.env configured, use
the isolated wrapper rather than launching that test directly:

```sh
cd agent
uv run --no-project --with-requirements requirements.txt python ../messaging/scripts/test-brain-offline.py
```

The wrapper runs the unchanged brain assertions, disables dotenv reloading,
blocks external requests.Session HTTP and asserts that no live message/call
delivery was dispatched. Blocked data-tool HTTP attempts are counted separately.
This prevents the brain test's scripted approvals from texting a live line.

This is the messaging milestone. Image/screenshot forwarding, the full recovery walkthrough driven by brain prompts, Twilio fallback, Supabase migrations and the watcher still require follow-up. Unsupported content currently stops event processing without checkpointing it; resolve that event before restarting, rather than silently losing it.

Live verification on the teammate's existing line confirmed alert receipt and a hello response to ping. NVIDIA's model catalog exposed `nvidia/nemotron-3-nano-omni-30b-a3b-reasoning`; this Nano endpoint accepted the account key and correctly classified the synthetic checks “no that was not me” as `no`, and “I told him my PIN” as `info` with `shared: [pin]`. The other Nano catalog entry returned account-level 404. D-035/D-039 now prefer Lightning, verified live with HTTP 200 and thinking disabled. Production reply interpretation is in the brain. This does not establish free-form recovery approvals end to end.

## Real reply integration (D-039)

`MOCK=1` replays a scripted fixture and intentionally ignores replies. To test acknowledgment and recovery, put the NVIDIA key in the gitignored agent/.env, use current model names from agent/.env.example, then start the brain with `MOCK=0`. Confirm GET /health reports mock=false before playing T2 and replying. Only the existing allowlisted teammate line should receive demo texts.

Live recovery verified after D-039/D-042 and PR #49: the teammate's NO reached
the real workflow, Step 1 of 4 was delivered unchanged, one YES applied only
the synthetic reset_pin action, and Step 2 of 4 was delivered. The teammate
confirmed Step 2 receipt; the other three actions remained awaiting approval.
Messaging made no direct approval calls. The local run used 180-second alert
and 600-second recovery windows to allow time for the interactive phone check.
